# v1.4.1 翻译失败修复

## 已复现的原因

MiniMax 旧型号 `MiniMax-Text-01` 返回：

```text
HTTP 404: The model "MiniMax-Text-01" is no longer available. (2069)
```

旧版只显示失败数量，具体原因藏在段落的 DOM 属性中；旧模型的缓存仍能显示译文，造成同页部分成功、部分失败的现象。模型下线无法通过重试恢复，需要在设置中选择供应商仍支持、且账户有权限的模型。

MiniMax 预设的模型提示已更新为 `MiniMax-M3.1-Flash`，并默认使用 `reasoning_effort: low` 减少段落翻译的推理耗时。用户的额外请求体参数可以覆盖此值。升级不会擅自替换其他用户已保存的模型或服务地址。

官方资料：[支持的模型与参数](https://platform.minimax.io/docs/api-reference/text-openai-api)、[模型列表及退役公告](https://platform.minimax.io/docs/faq/models)。模型供应商可能继续调整可用型号，请以其最新文档为准。

## 恢复操作

1. 打开插件的「更多设置」，检查模型、地址、鉴权和账户额度。
2. 点击「测试连接」，确认能返回真实译文，再保存引擎。
3. 回到页面，在插件面板点击「重试失败段落」。已有成功译文会保留。
4. 如果刚重新加载了未打包扩展，请先刷新目标网页，使内容脚本更新。

## 行为变化

- 面板显示服务错误及成功、失败数量，失败段落保留原文，不把空结果伪装成翻译成功。
- 模型不可用、鉴权失败、额度不足、候选地址全部不可用时，暂停本页后续请求。同一配置短期内共享故障状态，修正模型或密钥后可立即重试。
- 网络故障和 HTTP 408、425、429、500、502、503、504 在原地址最多自动重试两次，采用退避并遵循 `Retry-After`；重试耗尽后暂停。服务要求等待超过 30 秒时，直接提示等待，避免挂起消息通道。
- 全局和页面请求并发上限均为 2，多个标签页、iframe 共用后台的并发限制。
- HTTP 200 中的错误对象和 `base_resp.status_code` 也作为错误处理；推理内容不再作为正式译文兜底。
- 请求超时覆盖完整响应体读取，不在收到响应头时提前清除。
- 批量编号无法对齐时，只补翻对应小批次。服务错误不会再触发逐条请求风暴；逐条补翻中的局部失败也不会丢掉其他成功结果。
- 模型、地址、提示词、术语变化进入缓存指纹，避免旧缓存掩盖配置变化。
- 停止翻译后，晚到的请求错误不会重新污染页面；增量观察中同时出现译文节点和页面新内容时，仍处理真正的新内容。
- 修复安装、启动事件重叠时重复创建右键菜单的报错。

## 回归验证

在项目父目录启动静态服务器（端口 8766），再从项目目录串行运行：

```bash
python3 test/verify_reliability.py --ext .
python3 test/verify_ai.py --ext .
python3 test/verify_popup.py --ext . \
  --url http://127.0.0.1:8766/bilingual-reader/demo/demo.html
```

故障注入覆盖模型下线、共享探测、限流、网络失败、响应体超时、HTTP 200 错误、服务故障、局部结果保留、批量补翻、空译文、停止还原和混合增量更新；并在真实扩展消息通道中验证错误展示、修正后补翻和缓存隔离。全部使用隔离的 Chrome 配置与模拟服务，不读取用户配置或调用付费 API。

可用 `--source-ref v1.4.0` 将故障注入断言对旧版源码运行，以确认这些测试能够捕获回归；旧版预期失败。

2026-11-05 验证结果：25 项可靠性检查通过（其中包含原有 67 项 DOM 测试）、35 项 API 兼容性断言通过、弹窗操作检查全部通过。旧版在 16 项故障注入场景中有 14 项失败。重新加载实际 Chrome 中的 1.4.1 扩展后，真实 MiniMax 接口测试连接成功，公开演示页已译 51 段、面板无失败。
